# Cel

Wprowadzić jeden wspólny, rodzinno-neutralny builder v1 przyjmujący obowiązkowy `trackId`. Builder czyta wyłącznie `content/<trackId>/<nodeId>/<mentalUnitId>.json`, waliduje pytania wspólnym kontraktem SIMP-01 i deterministycznie zapisuje `dist/<trackId>.json` oraz wpis locka `{trackId, contentVersion, questionCount, sha256}`. Każdy z dziewięciu tracków ma być niezależnie walidowalny, testowalny i budowalny w hermetycznym fixture; pełny gate ma potwierdzać dokładnie dziewięć wpisów. SIMP-02 tworzy mechanizm, ale nie migruje produkcyjnych banków — rzeczywiste pliki dziewięciu tracków należą do SIMP-03.

Ocena przed implementacją: dopasowanie do celu i architektury `0,93` — jeden builder realizuje docelową granicę per track bez utrwalania rodzinnych pipeline'ów; prostota `0,88` — jeden moduł, jeden CLI i jeden lock, bez manifestów pośrednich; ryzyko `0,84` — testy izolacji, deterministyczności i atomowego zapisu ograniczają drift, a brak produkcyjnych wejść jest jawny zamiast maskowany pustymi artefaktami; utrzymywalność `0,91` — wspólna walidacja i kanoniczne bajty pozostawiają tylko track jako granicę pracy. Minimum: `0,84`.

# Ustalenia

SIMP-01 dostarczył katalog dokładnie dziewięciu tracków, schema, walidator i score function, lecz repo nie ma jeszcze `content/<trackId>/`; tworzenie pustych lub placeholderowych banków jest zabronione. Dlatego zdolność wszystkich dziewięciu wejść musi być dowiedziona przez testowy workspace z rzeczywistymi pytaniami fixture, a CLI na brakującym produkcyjnym wejściu ma zakończyć się jawnym błędem. `contentVersion` nie jest polem pytania; zostanie dopisane do kanonicznego katalogu jako metadata tracka, z wartościami przypiętymi do Candidate Manifest ACC-02, i zweryfikowane jako dokładna część katalogu. Artefakt będzie zawierał tylko `schemaVersion`, `trackId`, `contentVersion` i posortowane pytania. Hash locka jest SHA-256 dokładnych kanonicznych bajtów artefaktu. Builder odrzuca nieznany track, brak źródła, puste źródło, złą ścieżkę identity, duplikaty `questionId`, obce `trackId` oraz rozjazd katalogu. Indywidualny build nie skanuje ani nie nadpisuje artefaktów pozostałych tracków; pełny build iteruje dokładny katalog. Legacy pipeline pozostaje aktywny do SIMP-05 i nie jest importowany ani rozszerzany.

# Podejście

Rozszerzyć `content/catalog.json` i jego walidację o obowiązkowy `contentVersion` per track. Dodać `scripts/build.mjs` jako wspólną bibliotekę i CLI z operacjami `validate`, `test`, `build` oraz `build-all`, wymagającymi `--track` poza pełnym gate’em. Moduł rekurencyjnie zbiera wyłącznie pliki JSON spod wskazanego tracka, wymusza ścieżkę `<nodeId>/<mentalUnitId>.json`, wspólny contract i unikalność pytań, a zapis artefaktu i pojedynczego `dist/content-lock.json` wykonuje deterministycznie oraz bez dotykania innych wpisów. Dodać testy buildera korzystające z tymczasowego workspace’u: osobny validate/test/build każdego z 9 tracków, dokładnie 9 wpisów pełnego locka, powtarzalne bajty i SHA, zmiana jednego banku zmienia tylko jego artefakt/wpis, oraz negatywne przypadki braku/pustego wejścia, identity/path mismatch, duplikatu i nieznanego tracka. Dodać skrypty `content:validate`, `content:test`, `content:build` i pełny gate do `package.json`, zaktualizować README tylko o nową nieprodukcyjną ścieżkę i uruchomić test buildera, kontraktu oraz pełne `npm test`. Po niezależnym QA sporządzić raport, zaktualizować plan, commitować i publikować wyłącznie spójny zakres SIMP-02.
