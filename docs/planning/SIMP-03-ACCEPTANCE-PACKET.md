# Cel

Mechanicznie przenieść dokładnie dziewięć zaakceptowanych banków do jednego kanonicznego formatu, zachowując bez zmian learner-visible tekst, stabilne `questionId`, przypisanie `trackId`/`nodeId`/`mentalUnitId`, zbiór poprawnych odpowiedzi i istniejącą semantykę scoringu. Wynik zawiera dokładnie 9 tracków, 117 nodów, 932 mental unity i 16 041 pytań oraz buduje dziewięć niezależnych artefaktów SIMP-02. Migracja przebiega w trzech bramkowanych fazach: A — bezstratny kontrakt i oracle scoringu; B — jednorazowa materializacja; C — trwałe evidence i usunięcie writera. Żadna faza nie zmienia treści pytań, aplikacji ani legacy źródeł, które pozostają aktywne do SIMP-05.

Aktualizacja po audycie whitespace z 11 września 2026: exact preservation obejmuje również istniejący leading/trailing whitespace w polach learner-visible. Kontrakt nadal odrzuca surrounding whitespace w identyfikatorach, kluczach odpowiedzi, `difficulty` i `sourceRefs`; nie wolno trimować ani poprawiać źródła podczas migracji.

Ocena przeprojektowanego podejścia: dopasowanie do celu i architektury `0,92` — rozdziela kontrakt, zapis i trwały dowód bez tworzenia nowego aktywnego pipeline'u; prostota `0,82` — jedna projekcja pytania, jeden tymczasowy writer i jeden prosty verifier snapshotu; ryzyko `0,84` — każda faza ma stop condition, exact inventory, per-item hash, test równoważności scoringu i odwracalny cutover całego drzewa; utrzymywalność `0,87` — po fazie C pozostają kanoniczne JSON-y, builder i read-only verifier bez parserów legacy. Minimum: `0,82`.

Ocena najmniejszej korekty kontraktu po audycie: dopasowanie do celu i architektury `0,95` — oddziela politykę learner-visible text od identity bez zmiany canonical shape; prostota `0,92` — jedna jawna funkcja walidacji tekstu obok istniejącej walidacji trim-clean; ryzyko `0,89` — dopuszczenie dotyczy tylko tekstu, a regresje utrzymują restrykcje identyfikatorów i dowodzą exact preservation; utrzymywalność `0,93` — nazwy walidatorów kodują dwie różne polityki zamiast ukrytego wyjątku dla jednego promptu. Minimum: `0,89`.

# Ustalenia

Baseline ACC przechodzi i obejmuje per track 2568/1569/300/3404/1766/2981/1288/752/1413 pytań, łącznie 9/117/932/16 041. Cztery source envelopes mapują identity jednoznacznie: certification `itemId/nodeId/learningBlockId`, design `itemId/nodeId/mentalUnitId`, coding `id/taxonomy.roadmapNodeId/taxonomy.primaryMentalUnitId`; AI-901 zawsze używa itemowego `learningBlockId`. Obecny kontrakt nie mieści wszystkich danych: `feedback.details` występuje 16 041 razy, `option.explanation` 976 razy, complexity aliases w 248 pytaniach, a difficulty nie istnieje w 7889 certification items; część feedback maps źródłowo nie występuje. Jeden mental unit zawiera wiele pytań, więc jeden plik `<nodeId>/<mentalUnitId>.json` jest niepustą tablicą canonical questions. Brak difficulty jest wyłącznie `null`; brak constraints/sourceRefs/map pozostaje pustą tablicą albo brakiem opcjonalnego pola, bez syntetycznego tekstu. Rich `details` są zachowywane jako dokładna canonical-JSON wartość, a nie parafrazowane. Opcje zachowują opcjonalne `explanation`; complexity zachowuje alias→wartość i pełny zbiór accepted values. Scoring jest zamrożony przez pięć jawnych reguł: single exact-one, multiple poprawność decyzji per opcja bez fałszywego `correct`, ordering poprawne relacje sąsiednie, complexity i matrix poprawność per wymiar z alias normalization tylko dla complexity. Zmiana tych reguł jest stop condition, nie częścią migracji.

Pełny read-only audyt 876 plików i 16 041 itemów przeskanował rekurencyjnie 914 820 wartości tekstowych i 955 829 kluczy, w tym tablice. Potwierdził dokładnie jeden przypadek edge whitespace: `manual/source/coding-interview-dsa-problem-solving/linked_list/cycle-detection.json`, item `alg-linked-list-cycle-detection-11-entry-phase`, `items[10].prompt`, z jedną końcową spacją. Nie znaleziono CR, BOM, NUL ani whitespace/control characters w kluczach; surowe pliki nie zawierają BOM, NUL, CRLF ani bare CR. Wewnętrzny LF występuje w 177 wartościach i jest dozwoloną częścią treści. Audyt nie uzasadnia wyjątku po `questionId`; uzasadnia rozdzielenie kontraktu tekstu od kontraktu identity.

Canonical projection jest kompletna i stabilnie serializowana rekurencyjnie posortowanym JSON UTF-8 bez BOM/newline. Obejmuje identity; prompt/constraints/difficulty; wszystkie option/element/dimension IDs, labels/text/explanations i aliases; pełne accepted answers oraz scoring method; feedback reason, exact details i każdą istniejącą wiadomość błędu/pominięcia jako neutralny wpis `{kind,targetId,text}`; sourceRefs. Macierz cztery envelopes × pięć interakcji klasyfikuje każdy source item key jako: canonical learner/scoring data, identity, albo jawnie wyłączone authoring/publishing metadata. Nieznany klucz lub niewspierany details block zatrzymuje migrację. Trwałe evidence zawiera dla każdego itemu source path/raw item SHA, canonical question SHA i projection SHA oraz aggregate per track; verifier po migracji czyta wyłącznie canonical content i immutable evidence. Całe evidence leży wewnątrz migrowanego drzewa `content/`, więc content i dowód przechodzą jeden wspólny cutover. Tymczasowy writer i recovery pozostają dostępne aż do finalnego PASS oraz usunięcia markera/backupu; dopiero wtedy są usuwane przed commitem. Trwały test nie zależy od konwertera.

# Podejście

Faza A rozszerza pojedynczy schema/validator/scorer i builder bez alternatywnego formatu: `difficulty` string|null; opcjonalne option explanation i aliases; odpowiedzi wymiarowe przechowujące pełne accepted sets; neutralne feedback messages oraz exact JSON `details`; mental-unit file jako niepusta tablica pytań o wspólnej path identity. Dodaje tabelę mapowania pól oraz test oracle porównujący stare i nowe wyniki na deterministycznym korpusie odpowiedzi dla każdego itemu: wszystkie opcje single, wszystkie podzbiory multiple, canonical/reverse/adjacent-swap/omission ordering oraz accepted/wrong/alias/missing per dimension. Faza A musi mieć osobne QA PASS przed zapisem danych.

Mała korekta fazy A rozdziela walidację `id` od learner-visible text w JSON Schema, walidatorze runtime i tymczasowym writerze. Learner-visible `prompt`, `constraints`, option/element/value `text`, option `explanation`, dimension `label`, feedback `reason`, stringi w `feedback.details` oraz feedback message `text` muszą zawierać co najmniej jeden znak niebędący whitespace, ale zachowują surrounding whitespace i wewnętrzne LF bez normalizacji. `questionId`, `trackId`, `nodeId`, `mentalUnitId`, option/element/value/dimension IDs, accepted IDs, alias keys/targets, message `kind`/`targetId`, `difficulty` i `sourceRefs` pozostają trim-clean. Test regresyjny akceptuje i zachowuje bajtowo padded prompt, nadal odrzuca padded ID oraz whitespace-only text, a Draft 2020-12 i walidator runtime muszą być zgodne. Nie powstaje special case dla jednego itemu ani trim w writerze. Korekta wymaga niezależnego Luna/max PASS przed implementacją i osobnego worker–QA PASS przed powrotem do fazy B.

Faza B używa jednorazowego, niecommitowanego writera z czterema rozłącznymi adapterami envelope i pięcioma wspólnymi mapperami interakcji. Najpierw waliduje aktualne source/item manifests ACC, pełną macierz kluczy i scoring oracle; następnie generuje kompletne drzewo `content/` wraz z katalogiem i evidence pod jednoznaczną ścieżką staging, grupuje po dokładnym node/MU, liczy per-item evidence i porównuje exact identity sets, projection hashes oraz 9/117/932/16 041. Per-track i pełne validate/test/build, trwały verifier oraz niezależne QA działają najpierw na staging tree. Każda różnica lub unsupported shape usuwa wyłącznie staging i pozostawia aktywne `content/` bez zmian.

Faza C rozpoczyna cutover dopiero po PASS stagingu i QA. Najpierw zapisuje poza `content/` kanoniczny marker z SHA całego staging tree, SHA dotychczasowego drzewa i stanem `prepared`; następnie zmienia nazwę dotychczasowego `content/` na jednoznaczny backup, aktualizuje marker na `backup-created`, zmienia staging na `content/` i ustawia `activated`. Każdy krok jest idempotentny: przy błędzie lub wznowieniu stan markera i SHA rozstrzygają jedyną legalną akcję — dokończyć aktywację tylko gdy staging jest kompletny albo przywrócić backup; nie wolno nadpisywać niezgodnego drzewa. Po aktywacji ponownie uruchamia się per-track validate/test/build, build-all, trwały verifier i niezależne QA. Dowolny FAIL przed stanem `verified` przywraca backup i usuwa staging/output nowej rewizji. Dopiero finalny PASS ustawia `verified`, usuwa backup, marker, writer i tymczasowe adaptery. Recovery nie zależy od usuniętego kodu, ponieważ kod jest usuwany dopiero po zakończeniu i braku stanu do odzyskania; raport zapisuje SHA stanu przed/po, per-track source/canonical/projection aggregate SHA, counts i wyniki oracle. Pozostają tylko canonical data, wspólny contract/builder, mapping document, immutable evidence i verifier nieczytający legacy. Nie usuwa się legacy przed SIMP-05, nie zmienia aplikacji i nie uruchamia EPIC-09.
